# Project Documentation Rules

## 1. Ideas Are Not Commitments

Ideas and discussions do not automatically become project features or requirements.

An idea remains an idea unless explicitly approved by the project owner.

## 2. Feature Versions Require Approval

Feature versions represent approved project configurations or development stages.

Discussion, research, implementation, or testing does not automatically make something part of a feature version.

The project owner must explicitly approve the inclusion of a feature in a feature version.

## 3. Master Requires Approval

The Master represents the approved project configuration.

Nothing is automatically added to the Master.

The project owner must explicitly approve changes to the Master.

## 4. Research Is Traceable

Research findings should be linked to the sources that support them.

Research sources receive stable reference IDs.

Research should distinguish documented evidence from interpretation or uncertainty.

## 5. References Are Version-Aware

Each Feature Version has its own reference list.

The Master has its own reference list.

Reference IDs should remain stable once assigned.

## 6. AI Assistance Is Not Automatically Permanent

AI assistance is not automatically entered into the permanent project documentation.

AI-assisted work may first exist as a draft.

The project owner reviews and edits AI records before they are published as permanent documentation.

The project documentation should distinguish AI contribution from the project owner's own work, implementation, testing, and verification.

## 7. Git Records Change History

Git records changes to the project repositories.

Branches represent development work or temporary lines of development.

Commits provide a history of changes.

The documentation provides the permanent explanation of what happened, why it happened, and what evidence supports it.

## 8. Jira Records Planned Work

Jira is used to track work that needs to be completed.

Git records what changed.

Project documentation records what happened, why decisions were made, and what evidence supports the work.

## 9. Testing Requires Evidence

Testing records should document the objective, method, expected result, actual result, and conclusion.

Evidence should be included where applicable.

Examples of evidence include test data, measurements, photographs, logs, screenshots, serial output, and relevant Git commits.

## 10. Supervisor Meetings Are Recorded

Supervisor meetings and feedback may be recorded as project activities or meeting records.

Feedback and resulting actions should be documented.

Supervisor oversight does not automatically constitute approval of project features, requirements, or the Master.

## 11. The Project Owner Is the Final Authority

The project owner makes the final decisions regarding project requirements, design decisions, feature versions, and the Master project.

The documentation system and AI assistance support the project process but do not make project decisions on behalf of the project owner.

## 12. Approval Boundary

The following require explicit project-owner approval before being treated as committed project content:

- Feature Version contents
- Master contents
- Major project requirements
- Major design decisions where commitment is required
- Promotion of an idea into an approved feature
- Promotion of a Feature Version or feature into the Master

Discussion, suggestions, research, and drafts do not constitute approval.
